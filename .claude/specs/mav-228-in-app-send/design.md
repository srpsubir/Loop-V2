## Section 2: Service wiring

### Call graph (happy path — user clicks Send)

```
StoryScreen (renderer)
  └─ MessageComposer.tsx — user edits textarea, clicks Send
       └─ window.loop.whatsapp.sendMessage(jid, text)          [preload bridge]
            └─ ipcMain.handle('whatsapp:sendMessage', ...)      [ipc.ts]
                 ├─ validate: jid format, text non-empty, text ≤ 4096 chars
                 ├─ WhatsAppManager.getInstance().sendMessage(jid, text)
                 │    └─ sock.sendMessage(jid, { text })        [whatsapp.ts]
                 ├─ patchState({ contacts: { [contactId]: { lastReachOutAt } } })
                 └─ getWindow()?.webContents.send('state:changed')
```

### JID normalisation (critical)

`Contact.whatsappId` is stored as a raw phone number (e.g. `447812345678`) or occasionally as a full JID (`447812345678@s.whatsapp.net`). Baileys `sock.sendMessage` requires a full JID.

Normalisation happens in `WhatsAppManager.sendMessage()`:
```
function normaliseJid(raw: string): string {
  if (raw.includes('@')) return raw          // already a JID
  return raw.replace(/[^0-9]/g, '') + '@s.whatsapp.net'
}
```

### Where it's set up

- `ipcMain.handle('whatsapp:sendMessage', ...)` registered in `registerAllHandlers()` in `ipc.ts` — same lifecycle as all other handlers (app startup).
- Preload bridge added to `src/preload/index.ts` alongside existing `shell.openWhatsApp`.
- `MessageComposer` rendered inside `StoryScreen` — no new route, no new screen.

### What observes what

- Renderer listens for `state:changed` via existing subscription in `App.tsx` — `lastReachOutAt` update flows through automatically, nudge suppression applies as normal.

## Section 3: Cross-system sync

This feature is **local-only**. No new cross-system sync introduced.

- Message is sent outbound via the existing Baileys WebSocket to WhatsApp's servers.
- `lastReachOutAt` written to local `state.json` only — same as the existing `shell:openWhatsApp` path.
- "View in WhatsApp" fallback link opens `https://web.whatsapp.com` in the default browser — this is a read-only navigation, not a send.

**Source of truth:** WhatsApp's servers for message delivery status. Loop does not track delivery receipts — sent = fired, not confirmed delivered.

## Section 4: Edge cases

| Scenario | Handling |
|---|---|
| WhatsApp not connected (`wa.getStatus() !== 'connected'`) | Hide composer entirely — show "Open in WhatsApp" button only (same as today). Composer only renders when status is `'connected'`. |
| Empty textarea | Send button disabled when `text.trim().length === 0`. |
| Text > 4096 chars | IPC handler rejects with error; composer shows inline error "Message too long". |
| `contact.whatsappId` is null/undefined | Composer not rendered — `StoryScreen` already gates on `contact.whatsappId` for the existing WA button. |
| Baileys `sock.sendMessage` throws | IPC handler catches, returns `{ ok: false, error: string }`. Composer shows inline error: "Couldn't send. Try opening WhatsApp directly." Composer returns to editable state (not stuck in sending). |
| Double-send (user clicks Send twice) | Send button disabled + `aria-busy` during sending state. IPC handler is not re-entrant risk since renderer gates it. |
| Group JID (`@g.us`) | `normaliseJid` passes it through unchanged — Baileys handles group sends identically. Composer renders for any contact with a `whatsappId`, group or DM. |
| WhatsApp disconnects mid-send | Baileys throws — caught by IPC handler, error surfaced as above. |
| Story has no `draftMessage` | Textarea renders empty. User types their own message. Send button disabled until text is non-empty. |
| Contact has no story yet (scan not run) | `StoryScreen` already handles this — composer would be inside story section, gated on story existing. If no story, no composer shown. |

## Section 5: Platform constraints

- **Baileys session required:** `WhatsAppManager.socket` must be non-null and connected. `sendMessage()` must guard with `if (!this.socket) throw new Error('not connected')`.
- **No macOS entitlement changes needed:** Baileys already has network access via the existing session. No new capabilities required.
- **Electron sandbox:** `sandbox: false` is already set (required for preload Node APIs) — no change.
- **IPC from renderer is untrusted:** Handler validates JID format (`/^\d+@(s\.whatsapp\.net|g\.us)$/` after normalisation) and text length. Non-string inputs rejected.
- **WhatsApp 4-device cap:** Baileys takes one linked-device slot. If user is already at 4 devices, Baileys link fails at connect time (existing issue, not introduced here). "View in WhatsApp" opening a browser tab takes another slot — harmless since it reuses an existing WhatsApp Web session if present.
- **Rate limiting:** WhatsApp Web protocol has no documented send rate limit for personal accounts. No throttling added for v1 — monitor via MAV-75.
